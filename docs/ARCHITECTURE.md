# 架構與新增遊戲

專案將共用的房間功能與個別遊戲規則分開。目前提供 4～8 人的「太空維修站」及 2～4 人的合作遊戲「加密通話」。各遊戲沿用邀請、座位、連線與部署方式，另有自己的規則與畫面模組。

平台程式、Linux 服務、帳號及部署路徑統一使用 `boardgame`，例如 `boardgame.service`、`/opt/boardgame`、`/etc/boardgame.env` 與 `/var/lib/boardgame`。`space-station` 只作為第一款遊戲的穩定識別碼及 Socket.IO namespace；`src/games/station` 仍是這款遊戲的模組。既有房間、回放、瀏覽器儲存鍵及加入憑證的計算規約維持相容，新增遊戲使用自己的識別碼，不共用第一款遊戲的 namespace。

## 組成

```text
React 前端
    ├─ 建房、邀請、等待室與連線狀態
    └─ 依遊戲識別碼選擇遊戲畫面
          │
          ├─ /api：房間、觀戰、復盤、分享與統計
          └─ /socket.io：遊戲同步與操作
                      │
Node.js 服務          ▼
    ├─ 房間層：建房、邀請、座位、房主權限
    ├─ 遊戲註冊表：遊戲定義與人數限制
    ├─ boardgame.io：規則執行、回合、狀態同步
    └─ 持久化：自訂本機 JSON adapter + 房間索引 JSON
```

遊戲註冊表是原始碼中的明確登錄機制，不提供上傳並執行任意遊戲程式的動態外掛功能。新增遊戲需要修改程式、通過測試並重新部署。

## 開發與正式執行

開發環境由 `npm run dev` 啟動 Vite 與 Node.js。瀏覽器連到 `localhost:5173`，Vite 將 API 與 Socket.IO 代理至 `127.0.0.1:3001`。

正式環境先執行 `npm run build`，並設定 `NODE_ENV=production`、HTTPS `PUBLIC_ORIGIN` 與建房密鑰。`npm start` 由 Node.js 同時提供 `dist/client` 和遊戲 API；Apache 將遊戲子網域的 HTTPS 請求代理至本機 Node.js。前端不需要知道對外的獨立 API 埠號。

## 房間與對局

房間層管理參與者與邀請，遊戲層管理對局進度。房號不能直接代表座位權限；座位名稱也不能作為身份憑證。

1. 建房請求先經過建房密鑰檢查，再由伺服器產生房號、邀請與座位 0 的玩家憑證；`hostPlayerID` 初始指向座位 0，之後可在房主離席時交接。
2. 使用者提供邀請與該次加入的隨機 `requestID`，選擇入座或觀戰。新入座檢查邀請時效、房間狀態與容量；新觀戰檢查邀請時效與觀戰身份上限。相同身份類型的請求重送會回傳先前結果，避免手機網路遺失回應時重複分配。
3. 邀請 fragment 在頁面載入時已清除並暫存於 `sessionStorage`；加入成功後保存玩家或觀戰憑證並清除暫存的加入資料。玩家在正式對局建立遊戲連線，觀戰者透過唯讀 HTTP 輪詢取得狀態。
4. 玩家傳送操作；伺服器依遊戲規則與當前狀態判定結果，再向各玩家發送各自可見的狀態。
5. 重新連線時，以既有憑證要求最新狀態。瀏覽器畫面不應自行推斷斷線期間發生的結果。
6. 正常終局或房主提前結束後，封存本局並建立新等待室；穩定房號、邀請及留存身份不變，`currentMatchID` 更新，所有玩家重新準備。前端依新 `matchID` 重建遊戲連線，歷史分享仍指向原局。

邀請連結分享的是加入機會，不包含分享者的座位或房主權限。房主重設邀請與開始遊戲，都需由伺服器檢查房主權限。

建房可省略遊戲，`gameSelected:false` 代表只集合、不允許準備或開局；舊房間缺省視為已選定。等待室固定提供 8 個參與席，與遊戲的開局人數上限分開。房主選擇遊戲時建立新的等待室對局、清除準備並原子發布房間指標，保留每個人的座位與憑證、觀戰身分、房主及邀請。較少人數的遊戲不會自動移走超額成員，只在開局時拒絕不符人數的請求；進行中不得換遊戲。

同房歷史以每局的 `gameName` 保存遊戲種類，回放、分享、結果與統計都依該局選擇遊戲定義，不能套用房間目前選定的遊戲。舊歷史尚無此欄位時沿用原房間遊戲，第一次換遊戲前補上原遊戲標籤，避免重啟後誤解讀舊對局。更換遊戲本身不產生完成局或中止紀錄。

等待室的 `switch-role` 由房間層處理，兩款遊戲共用。已認證成員可在參與／觀戰間切換，保留暱稱、邀請與歷史，觀戰不占玩家席位。新入座者未準備，其他玩家的準備與憑證保留。房主資格跟隨切換後的身分：玩家房主使用 `hostPlayerID`，觀戰房主使用 `hostObserverID`，另一個欄位為 `null`。主動離開房間才交給剩餘玩家；若無玩家則暫無房主，下一位入座者接任。正式對局不允許切換。

房主端點先驗證目前玩家或觀戰憑證，再比較同一身分類型的房主 ID；普通觀戰者不因此取得管理權。切換時新房主指向與新身分、重試收據一併原子發布；返回等待室及其他人加入不改變觀戰房主。舊房間沒有觀戰房主時沿用原玩家房主欄位，該欄位缺省仍採用最初的玩家座位 `0`，向前端回傳明確的房主欄位。歷史回放不公開目前房主，兩個欄位均為 `null`。

身分切換與 HTTP 準備／開局及遊戲操作使用同一房間佇列，核對來源憑證、當前 `matchID` 與容量。每次切換先建立獨立等待室，再一併發布房間指標、觀戰名單及恢復紀錄，換發新憑證並撤銷舊身分；發布失敗時舊等待室仍可使用。舊等待室不進入歷史或戰績。恢復紀錄保存雜湊，原請求可在重啟後重取仍有效的目標身分；目標離開、被移出或再次切換後，原請求不能復活它。

前端共用的 `RoleSwitcher` 提供切換操作，`SpectatorRoster` 在等待室及對局顯示觀戰者暱稱。瀏覽器同房只保存一個身分，其他分頁隨儲存事件切換；Web Locks 避免多分頁同時送出互相覆蓋的切換請求，待完成請求保存到成功恢復為止。這項操作需新版瀏覽器及 HTTPS／localhost。

## 遊戲規則與秘密資訊

規則程式應保持可測試的狀態轉移，將遊戲 UI 與 Node.js 檔案存取等副作用移出規則模組。時間、亂數與勝敗條件應由伺服器使用一致的規則處理，避免由玩家任意提交結果。

boardgame.io 的完整狀態保留於伺服器。每個玩家的 `playerView` 僅包含公開資訊與該玩家被允許取得的私人資訊；觀戰 HTTP 另外經過身份驗證及 `observerView` 投影。盲視角只回傳當時公開資訊，上帝視角在進行中即可回傳所有參與者的角色、設備組成與剩餘牌序，仍排除未發角色、亂數種子與框架內部資料。需要使用完整秘密狀態的操作應在伺服器執行，避免客戶端的樂觀更新使用不完整資料產生錯誤結果。

玩家憑證不能取得進行中的觀戰視角，但本版沒有帳號身分去重，不能阻止同一人用另一個瀏覽器取得觀戰憑證，或觀戰者私下轉告資訊。使用上帝觀戰功能需要朋友間的信任約定。

公開操作紀錄與內部保存資料具有不同可見範圍。遊戲結束是否公開角色或剩餘資訊，應是規則明確定義的行為，不能因為結束就直接回傳全部伺服器資料。

太空維修站在宣稱階段按玩家是否已提交過濾數字：尚未提交者只收到其他人的 `claimSubmitted` 進度，`claim` 為 `null`；提交後才可讀取其他人的數字。這個進度旗標只存在於投影，重複套用 `playerView` 時仍保留，原始狀態以 `claim` 判斷提交。操作日誌的參數持續遮蔽，狀態更新、差異更新與重新同步均套用相同規則。觀戰與賽後復盤維持既有宣稱可見性。

太空維修站 0.3 的新局標示 `G.rulesVersion = 2`。`publicCards` 保存本輪固定牌位及已揭牌種類，`secret.cards` 保留整列牌序；`cardCount` 和私人組成只計尚未翻開的牌。每輪資訊確認後進入 `claiming`，宣稱獨立於真實組成。公開預選使用每局遞增的 `selectionID`，真正揭牌時必須同時符合目前行動者、輪次、目標、位置及識別值，避免其他瀏覽器、延遲對話框或過期操作檢修到不同的牌。新版所有狀態轉移都由伺服器裁定，前端不自行揭牌。

`rulesVersion` 缺省的舊局保留原本的確認、兩參數揭牌與緊縮牌列行為。歷史快照依當時版本渲染，不重寫既有回放、不補造宣稱或預選。新增其他遊戲時應自行選擇版本欄位及相容策略，不依賴第一款遊戲的牌位或階段。

0.7 版開始的新太空維修站對局使用 `rulesVersion = 3`，在非終局輪末進入 `round-review`。牌桌及檢修紀錄保持不變，`acknowledgeRound(round)` 只接受該輪參與者的一次確認；所有人確認後才抽取剩餘暗牌並重新分配。與公開宣稱相同，這個操作允許同一輪的並行確認，但以輪次拒絕延遲到下一輪的請求。確認狀態隨遊戲存檔和回放保存；版本 2 保留立即換輪行為。

版本 3 的前端資訊確認使用 `acknowledgeBriefing(round)`，同樣允許同輪多人同時送出並拒絕過期輪次；舊 `acknowledge()` 保留原本的狀態版本檢查，供舊前端與舊局使用。

0.8 版在版本 3 對局的 `beginGame` 中，以 boardgame.io 的伺服器亂數從實際玩家 ID 抽出首位檢修者。抽選只在開局執行一次，結果隨對局狀態保存；後續輪次沿用最後被揭牌者，載入舊局不重新抽選。

太空維修站的即時音效只讀公開揭牌紀錄與目前可行動者，不依賴秘密陣營或未翻牌內容。玩家與即時觀戰各維護收到的事件基準；首次載入、斷線恢復及視角切換僅重設基準，不補播歷史。Web Audio 在使用者操作後啟用，以本機合成短音播放，靜音偏好保存在瀏覽器；音訊失敗不阻擋遊戲操作。復盤 renderer 不掛載即時音效。

遊戲登錄可選填 `completedDisplayMs(state)`，指定終局畫面停留時間；版本 3 太空維修站為 8000 毫秒，其餘目前為 0。房間索引保存目前對局的截止時間，讓重啟與多次輪詢維持同一期限。此期間對局已完成，勝敗與回放正常可讀；生命週期在期限後建立新等待室，並清除舊截止時間。

## 持久化與重啟

遊戲狀態使用 `src/server/storage.ts` 的 `FileStorage`，繼承 boardgame.io 的非同步儲存介面。每個對局存成 `DATA_DIR/matches/<16字元對局ID>.json`，包含格式版本、對局識別碼、`initialState`、`state`、`metadata`、完整 `log` 與回放欄位。房間層另將穩定房號、目前對局、歷史對局、目前房主、遊戲識別碼、邀請、觀戰身份與回放分享的授權範圍存於 `DATA_DIR/rooms.json`。舊房間缺少 `currentMatchID` 時以原房號作為對局 ID。等待室實際人數從有效入座身份計算，歷史局人數依正式開局的參與者保存，不能套用下一局的名單。

採用自訂 adapter，是為了避開既有 FlatFile 實作依賴 `node-persist` 共用預設 instance 與定時寫入佇列的等待。這裡使用 Node.js 原生檔案 API，每房的讀寫依 Promise 佇列序列化，不需等待固定的寫入掃描週期。這不代表磁碟 I/O 沒有延遲；仍需在 Pi 5 上量測。

寫入會先建立同目錄的暫存檔，以 `flush: true` 同步檔案內容，再以 rename 替換完整對局檔。Windows 若暫時遇到 `EPERM`、`EACCES` 或 `EBUSY`，對局與房間索引的替換最多嘗試 6 次、合計等待 620ms；不先刪除原檔，持續失敗仍回報錯誤。其他錯誤與 Linux 維持直接回報。讀取重新解析 JSON，呼叫端不能透過修改回傳物件改到另一個請求的記憶體資料。狀態更新會保留 metadata 並追加 deltalog；metadata 更新則保留狀態與紀錄。

`src/server/room-isolation.test.ts` 以同一個真實 HTTP／Socket.IO 伺服器同時執行 4、5、6 人三房，驗證加入、宣稱、公開預選、揭牌、觀戰權限、跨房憑證拒絕、終局回放、全站統計與重啟恢復。這是朋友多桌同時遊玩的功能測試，不是 Pi 5 的負載或吞吐量保證。

此原子替換僅處理單一對局檔的更新，不保證斷電存活，也沒有對局檔與 `rooms.json` 之間的交易。兩部分共同構成一個可恢復的對局，備份時需保留完整 `DATA_DIR`。

目前採單一 Node.js 程序，每份資料目錄只由一個 adapter instance 使用；沒有跨程序檔案鎖。不要啟動多個程序或多個 instance 同時寫入同一份資料。資料格式或遊戲規則變更時，要評估舊資料相容性；未設計遷移程序前，優先等進行中的對局結束再更新。舊 FlatFile 資料不會自動轉換成此格式。

0.2 版的 schema 1 增加 `replayFrames` 與 `replayComplete`。從正式開局起，每個有效狀態版本保存 `{stateID, at, G}`，與目前狀態一起原子寫入；等待室不加入回放，重複／較舊版本不會再次加入。舊資料缺乏完整歷史時保持 `complete: false`，不根據現在的牌面補造過去；正式對局版本跳號也會標為不完整。回放 API 僅在終局開放，依遊戲的 `observerView` 過濾，完全不傳出 metadata、RNG、plugins 或座位憑證。不完整歷史仍可供 API 識別，但前端不提供完整時間軸或發行分享。

等待室由 HTTP 的 ready/start 操作管理；建立時預留房間的 8 個參與席，真正開局才依所選遊戲登錄的人數範圍，使用當時入座且全員準備的玩家重建初始對局。`startMatch` 在單一檔案內原子替換初始狀態、目前狀態、玩家 metadata 與回放；與入座、選遊戲使用相同房間佇列。Socket.IO 不接受 `startGame`，避免繞過 HTTP 的實際參與者檢查。前端在進入正式對局後才掛載 boardgame.io client。

觀戰者使用獨立 HTTP 輪詢及憑證，不加入 boardgame.io 的玩家 metadata。即時 `RoomInfo.spectators` 對房內成員提供 `{id,name}` 名單，歷史回放與分享則回空陣列，不把目前觀戰者帶進過去對局。全站統計由 `collectStatistics` 逐局讀取已完成結果，不另保存可重複累加的計數器；未完成局不計，舊版完整勝敗結果可納入。統計按遊戲、勝方、原因與實際玩家人數彙整，不提供房號、暱稱、個人戰績或排名。這適合朋友的小型單程序服務，大量歷史資料時應另建可重建的統計索引。

分享回放限正常結束且 `complete: true` 的對局，另發行 7 天有效的獨立隨機 token，索引保存雜湊、原對局 ID、到期時間、起始步驟與視角。`/api/replays/:roomId` 僅按 token 綁定的原局與視角回傳過濾歷史；原房開始下一局不會改變分享內容。指定步驟是初始播放位置，不是裁切片段，收件者不能升級視角或取得其他權限。房主可整批撤銷房內所有局的分享。戰報圖片由前端 canvas 只取所選快照的公開事件、暱稱與進度繪製，無論目前是否使用上帝視角都不含秘密牌面、網址或憑證，也不需外部圖片、字型或上傳服務。

短暫斷線重新同步與服務重啟後恢復，是不同驗收項目。後者同時依賴完整持久化、檔案權限、啟動載入流程及原本玩家仍保存憑證。備份還原也要獨立測試。

邀請 24 小時到期只阻止新的入座與觀戰身份，不會撤銷既有身份或移除房間。已成功加入且未被撤銷的冪等請求仍可重取原結果。全員離線逾重連寬限會中止目前對局並回到等待室；此功能不會刪除房間、歷史或備份，目前仍沒有自動清理舊資料的程序。

## 新增遊戲的責任分工

伺服器端登錄位置是 `src/games/registry.ts`。`gameDefinitions` 的每個項目符合下列欄位，由 `getGameDefinition(id)` 查詢；`publicGameDefinitions()` 僅提供前端可展示的資訊，不回傳遊戲函式。

```ts
interface GameDefinition {
  id: string;
  name: string;
  description: string;
  minPlayers: number;
  maxPlayers: number;
  game: Game<any>;
  isJoinable: (state: any) => boolean;
  startSetupData: (participantIDs: string[]) => Record<string, unknown>;
  observerView: (state: any, perspective: 'blind' | 'god') => unknown;
  getOutcome: (state: any) => { winner: string; reason: string; roles: Record<string, string> } | null;
}
```

`isJoinable` 是必填函式，收到的是該遊戲的 `G` 狀態。兩款遊戲只在 `G.status === 'lobby'` 時回傳 `true`；伺服器以此判斷能否加入新玩家、切換參與／觀戰身分、修改準備狀態或開始對局。它不限制重設邀請或加入觀戰。公開遊戲列表只回傳 `id`、`name`、`description`、`minPlayers`、`maxPlayers`，不回傳函式。

`startSetupData(participantIDs)` 讓伺服器用實際座位清單與正確人數直接初始化正式對局。清單由伺服器 metadata 取得，不採用客戶端傳值；移出玩家後可能為 `['0', '2', '3', '4']`，不能假定編號連續，也不能改號導致既有憑證對到別人的座位。遊戲 setup、回合 playOrder、配牌與視角必須使用這份清單，`ctx.numPlayers` 則是實際參與人數。

`observerView` 明確列出允許的觀戰／回放欄位；`getOutcome` 僅在合法終局回傳結果，供統計及賽後分享授權。房主重設邀請不再受開局限制，但開始後邀請只能建立新觀戰身份。新遊戲也需提供前端唯讀快照 renderer；等待室的共用狀態約定為 `G.status`、`G.players[id].ready`。

將規則放進自己的 `src/games/<遊戲目錄>/`，在登錄表新增定義，再於 `src/client` 的遊戲畫面選擇層加入同一個 `id` 對應的 React 元件。伺服器規則模組不要匯入瀏覽器專用元件。

加密通話使用 `encrypted-call` 作為遊戲 ID 與 Socket.IO namespace，規則在 `src/games/cipher/game.ts`。全員可操作的遊戲使用每房共用的伺服器序列佇列，並對適用的 move 啟用 `ignoreStaleStateID`，避免同一個舊狀態版本送出的兩位玩家操作只接受其中一人。這不代表忽略合法性：每個操作仍檢查參與者、狀態、頻段與 `epoch`；出牌另要求符合伺服器目前的最小手牌。階段轉換遞增 `epoch`，避免失序、暫停、表決或換頻段後執行舊指令。數值依伺服器接收順序裁定，不使用客戶端時間戳重新排序。

加密通話的 `private[id].cards` 僅回傳本人手牌；已授權上帝觀戰可取得已發手牌，盲視角只取公開狀態。開局同步、失序後同步及換頻段確認由遊戲規則控制；通用等待室的準備與開局仍走原本 HTTP 流程。正常結果為 `agents / all-levels` 或 `intercepted / cover-blown`，所有參與者的角色都屬 `agents`。前端以 `cooperative` 和 `resultLabels` 表示全隊成敗，統計只展示一支特務小隊。

前端共用的 `SnapshotProps` 與 `PosterOptions` 定義在 `src/client/game-types.ts`；遊戲的唯讀快照不接收 move。`BattleReport` 依遊戲 ID 選擇 PNG renderer；每個 renderer 都必須明確只讀公開欄位，即使傳入上帝視角也不能把秘密手牌畫入圖片。新遊戲必須同時登錄玩家畫面、規則、快照、結果標籤及戰報 renderer。

每款遊戲至少需提供穩定的識別碼、顯示名稱、人數範圍、boardgame.io 遊戲定義、玩家視角過濾與前端畫面。登錄新遊戲時，伺服器與前端應使用一致的識別碼；不能只在前端新增按鈕而未註冊伺服器規則。

新增遊戲應驗證：

- 所有允許人數的開局條件與完整勝敗流程。
- 每個操作在錯誤回合、錯誤階段、錯誤操作者或不合法參數時被拒。
- 各玩家與沒有合法身份者都只能取得允許的資訊。
- 重新整理、重連、服務重啟與重複操作不破壞進度。
- 素材來源、授權、手機操作與無障礙基本需求。

共用房間層應維持對遊戲規則的最少了解；個別遊戲專屬條件放在自己的規則中。需要擴充共用介面時，應一次更新伺服器、前端與對應測試，避免同一識別碼在兩端代表不同規則。

## 健康檢查

`GET /api/health` 回傳 `{"status":"ok"}`，供部署後確認 HTTP 服務存活。它不驗證一整局遊戲能否完成、持久化資料是否可恢復，或所有外部玩家是否能建立 WebSocket 連線。

## 版本選擇

boardgame.io 發布套件與 GitHub main 的內容可能不同，不能僅憑 `package.json` 的版本字串推定行為一致。本專案以依賴鎖定檔與測試結果為準。更新 Node.js、boardgame.io、React 或 Socket.IO 時，重新檢查建置、連線、憑證、秘密資訊與持久化相容性。
